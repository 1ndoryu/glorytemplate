## 2003A-28 — Fix definitivo pull-to-refresh (publicaciones + samples)
- **Que:** Pull-to-refresh tenía 2 bugs: (1) `obtenerScrollTop()` caía a `window.scrollY` (siempre 0 en SPA porque el body no scrollea) cuando el elemento ref no tenía `overflow-y: auto`. El scroll real vive en `.areaContenido` (ancestro), no en window. Esto causaba que PTR se activara en cualquier posición en publicaciones. Fix: nueva función `buscarAncestroScrollable()` recorre padres del DOM hasta encontrar el primer ancestro con `overflow-y: auto/scroll` y usa su `scrollTop`. (2) `useEffect` usaba `elementoRef` (useRef) que no dispara re-render. FeedSamples tiene early returns (skeleton/offline) que renderizan sin `pullToRefresh.contenedorRef`. Cuando la data carga y el ref se adjunta, useEffect no re-ejecutaba porque sus deps `[habilitado, umbral, resistencia]` no cambiaban → listeners nunca se registraban → PTR nunca funcionaba en samples. Fix: cambiar `useRef` por `useState` para el elemento — el cambio null→div dispara re-render y useEffect re-ejecuta.
- **Archivos:** App/React/hooks/usePullToRefresh.ts
- **Gotchas:** El ancestro scrollable se cachea una vez al montar el efecto para evitar `getComputedStyle` en cada touchmove. En layout con panel lateral, `.contenedorContenido` también tiene `overflow-y: auto` y es más cercano al feed — la búsqueda de ancestro lo encuentra correctamente.
- **Sentinel:** No aplica.

## 2003A-27 — Plan de optimización SQL feed algorítmico
- **Que:** Investigación y plan detallado para reducir el query CTE del feed de 696ms a <100ms, escalable a 1M usuarios. Análisis del EXPLAIN ANALYZE confirmó que los datos de timing son suficientemente detallados. Se identificaron 3 cuellos de botella principales: (1) `score_tags` CTE con `LATERAL UNNEST` = 493ms sort, (2) 2× Sort + WindowAgg para diversidad = 660-694ms acumulados, (3) 11 LEFT JOINs en base_scores = 105ms exclusivos. Se investigaron técnicas de Meta (fan-out on write), Twitter (two-phase ranking), TikTok (embedding recall) y YouTube (pre-computed candidate pools). Plan de 5 fases: (F1) Índices + separar flags UI + candidatos = ~450ms, (F2) Materializar tag affinity = ~200ms, (F3) Diversidad en PHP = ~150ms, (F4) Pipeline candidatos + pgvector HNSW = <100ms, (F5) Pre-computed feeds async = <10ms.
- **Archivos:** App/Agente/planes/plan-optimizacion-feed-sql-2026-03-20.md (plan completo)
- **Gotchas:** El patrón universal de redes sociales a escala es separar candidate generation (barato, pre-computed) de scoring detallado (caro, pocos candidatos). Kamples actualmente hace scoring detallado de TODOS los samples — esto no escala. La columna `tags_enriquecidos` ya existe como optimización previa. El SelectorCandidatos está inactivo (umbral 5,000 > 2,649 samples actuales).
- **Sentinel:** No aplica.

## 2003A-26 — Fix pull-to-refresh scroll Android
- **Que:** Al hacer scroll hacia abajo en la APK Android y luego intentar subir, el WebView activaba el pull-to-refresh nativo del navegador (recarga completa de página) en vez de simplemente scrollear hacia arriba. - **Gotchas:** `overscroll-behavior: none` en html es seguro porque la app tiene su propio PTR via touch events directos (`usePullToRefresh.ts`) que no depende de `overscroll-behavior`. El PTR custom usa `passive: false` + `e.preventDefault()` en touchmove y sigue funcionando. El fix Java con `getBridge().getWebView()` requiere que se llame después de `super.onCreate()` que es donde Capacitor inicializa el Bridge.

## 193A-100 — ERR_CONNECTION_CLOSED en polling /descargas/limites
- **Que:** El `useTopBar` hace polling a `/descargas/limites` cada 60s para actualizar créditos. `ERR_CONNECTION_CLOSED` es un error de keep-alive timeout del servidor — la conexión HTTP reutilizada se cierra por inactividad y el siguiente request falla antes de establecer una nueva. Es transitorio y se auto-recupera en el siguiente poll. El problema no era funcional sino de ruido en consola: `apiCliente.ts` logeaba TODO network failure como `[ERROR]`, incluyendo estos transitorios. Fix: GET requests con `TypeError` (indicativo de fallo de red) ahora se logean como `[WARN]` en vez de `[ERROR]`. También `obtenerLimites` bajó de `log.error` a `log.warn`.
- **Archivos:** apiCliente.ts (log condicional GET transitorio), apiDescargas.ts (warn en vez de error)
- **Gotchas:** `TypeError: Failed to fetch` es la señal genérica del browser para todo fallo de red pre-response (DNS, timeout, connection reset, etc.). No es un error de código. Solo aplica a GET porque POST/PUT/DELETE fallos sí ameritan ERROR.
- **Sentinel:** No aplica.

## 193A-73 — Badge verificado debajo del nombre en dropdown mensajes

## 2003A-4 — Pull-to-refresh solo se activa desde el top
